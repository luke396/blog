## AI 总结

本文记录了一次完整的图像分类任务实验过程,从基础的 CNN 理论到高级的预训练模型应用,展现了深度学习实战中的关键技术点和常见陷阱。

**核心技术发现:**

- **预训练模型的威力**: 使用预训练模型起手就能达到 60% 准确率,远超从头训练的效果,验证了迁移学习的重要性
- **数据处理陷阱**: 训练集正则化但测试集未正则化会导致分布不一致,是模型无法收敛的常见原因
- **Batch Normalization 设置**: 在只更新分类头的场景下,必须将预训练部分设为 eval 模式,否则 BN 层的统计信息更新会干扰原模型
- **测试集处理规范**: shuffle 不应该设为 True,保持统一顺序才方便比较;num_workers 可调整以减少 GPU 等待时间

**调参经验总结:**

- **Batch Size 的真实作用**: 不能简单追求跑满 GPU,更应该关注 batch size + lr 组合达到目标性能的时间,而非单次 epoch 耗时
- **数据增强的边界**: 增强后模型不收敛可能是噪音过多,模型已经学不到东西了
- **预训练模型调优策略**: 从头训练效率低且效果差,应优先考虑预训练模型 + 微调的方案

**微调 (Fine-tuning) 的完整流程:**

1. 加载预训练模型
2. 更换 forward 层以适配新任务的分类数
3. 更换 optimizer (如改用 AdamW 提高鲁棒性)
4. 选择合适的 scheduler 以稳定收敛

**CNN 理论补充:**

- 详细推导了 CNN 和 pooling 层输出尺寸的计算公式: $\text{Out}= \frac{{\text{Input} + 2\times \text{Padding} - \text{Kernel Size} }}{\text{Stride}} + 1$
- 解释了公式背后的直觉:可移动格子数除以步长就是移动步数

**实践价值:**

这份记录展现了真实的计算机视觉实验过程,既有成功的调优经验,也包含了失败的探索和从中获得的洞察,为深度学习实践者提供了宝贵的图像分类任务调参经验和迁移学习应用指导。

## 实验笔记

### PyTorch 多卡训练

- PyTorch 不会主动使用多卡进行训练，而是需要显式指定 `model = nn.DataParallel(model)` 在 `model.to(device)`

### Batch Size 与学习率的权衡

- batch size 虽然会影响训练的速度和所需要的 memory，但是最主要的作用，还是和学习率一起，作为需要同时变化的、重要的模型超参数，不能简单地追求跑满 GPU，当然相对高的 GPU 利用率总是经济的
- 更应该作为速度衡量的标准是，这个 batch size + lr 的组合，多长时间能把模型提升到想要的水平，而不仅仅是单次 epoch 的耗时

### 数据增强的常见问题

- 图片增强之后，怎么调参也不收敛，还有一个可能的原因，就是增强后的图片，噪音太多，模型已经学不到东西了
  - 看起来，我这次遇到的原因是，train 的数据正则化了，而 test 没有。这就导致二者的分布不一样，测试集能跟着提高才怪

### 预训练模型的重要性

- 显然，使用预训练模型 + 一点调整是更合适、效率更高、效果更好的
- 预训练模型真牛逼，起手就是 60%。比我自己苦哈哈来回调快多了，也有用多了！
  - 小反思，学习进度快，多见识很重要，很多细节可以不着急，以前傻逼呵呵在自己训练模型，肯定不是没用，但确实也有点太困在局部了，应该跳出来看看

### 测试集处理规范

- 测试集中 shuffle 不应该为 True，保持统一顺序才方便比较
- num_workers 也可以调整，帮助更快地读取数据，减少 GPU 的等待

### Batch Normalization 在预训练模型中的设置

- 对于预训练模型，只更新分类头的情景，应该把 batchnorm 设为 eval 模式
- 因为如果只设置成 train 模式，即使冻结梯度，其中内部的基于每个 batch 的 mean 等信息还会更新，这会干扰原来的 resnet 模型
- 如果模型没有 batchnorm 层，那就可以忽略这点

### 微调 (Fine-tuning) 的流程

微调，就是在加载预训练模型的基础上，在新的数据集上进行以下操作：

- **更换 forward**: 我们的任务与原任务可能分类数不同
- **更换 optimizer**: 更新参数选择的策略，AdamW 可能会更加鲁棒，防止过拟合，原有预训练模型可能是 SGD 训练的
- **选择 scheduler**: 选择更适配任务和 optimizer 的 lr 调度器，以稳定收敛

## CNN 输出尺寸计算

### 计算公式

> 更全面的计算参见 PyTorch 的相关文档[^1]

公式为：

$$
\text{Out}= \frac{{\text{Input} + 2\times \text{Padding} - \text{Kernel Size} }}{\text{Stride}} + 1
$$

### 公式背后的直觉

这里背后的直觉是，当给定 input size，加上 2 倍的 padding（这是因为我们会在输入的上下左右都添加），此时得到的是我们的 kernel 可以扫描的实际尺寸。

以行视角为例，等待扫描的实际尺寸减去 kernel size 得到的是 kernel 可以移动的格子数量。可移动数量除以每次移动步数减去 stride，就得到了 kernel 可以移动的步数，加上 1（未移动时会产生的结果），就是 kernel 在 input 尺寸添加 padding 的情况下，可以输出的结果数量，也就是 output 的行尺寸。

如果是方阵，就到此结果；如果不是方阵，把公式中的参数换成计算列的不同尺寸，计算即可。
